# n8n workflows as code — сборка, валидация, деплой

Пайплайн, который превращает low-code платформу автоматизации в нормально управляемый код:
логика живёт в git, конфигурация потока — артефакт сборки, деплой идёт из CI,
а не мышкой в интерфейсе на проде.

[![CI](https://github.com/shivanmi/n8n-workflow-cicd/actions/workflows/ci.yml/badge.svg)](https://github.com/shivanmi/n8n-workflow-cicd/actions/workflows/ci.yml)

---

## Зачем

Типичная проблема эксплуатации n8n в компании:

| Как обычно | Чем плохо |
|---|---|
| Поток правят в UI прямо на проде | Нет истории изменений, нет ревью, нет отката |
| Логика живёт внутри Code-нод | Её не видно в диффе, нельзя переиспользовать, нельзя протестировать |
| Деплой = «сохранил и надеюсь» | Активный поток публикуется мгновенно, ошибка уходит в прод |
| Бэкап = ручной экспорт, когда вспомнил | Восстановление зависит от дисциплины конкретного человека |

Этот репозиторий показывает другой подход:

- **Логика Code-нод — обычные `.js` файлы** в `src/code/`. Их видно в диффе,
  на них можно натравить линтер и тесты.
- **Поток описывается сборщиком** в `src/workflows/`: ноды, связи, параметры.
  Код Code-нод подставляется при сборке.
- **JSON потока — артефакт сборки**, он в `.gitignore`. Источник правды — код.
- **CI собирает, валидирует и деплоит.** Валидация проходит без доступа к n8n,
  поэтому пайплайн зелёный даже в форке без секретов.

## Быстрый старт

```bash
npm install          # зависимостей нет, но скрипты объявлены здесь
npm run build        # собирает dist/*.json из кода
npm run validate     # проверяет структуру, связи и типы нод
npm run deploy       # деплоит в n8n (нужны N8N_URL и N8N_API_KEY)
```

Локальный стенд, чтобы не проверять на проде:

```bash
cp .env.example .env
docker compose up -d
```

Поднимет n8n + PostgreSQL на `http://localhost:5678`. Дальше — создать API-ключ
в Settings → API, положить в `.env` и деплоить туда же.

## Как устроена сборка

```
src/code/*.js          ─┐
  чистые функции,       │
  бизнес-логика         │
                        ├──► tools/build.js ──► dist/<workflow>.json
src/workflows/*.js     ─┘         │
  описание нод и связей           │  подставляет код в параметр jsCode
                                  │  проставляет позиции, id, typeVersion
                                  ▼
                          tools/validate.js
                            • все ноды имеют имя и тип
                            • имена уникальны
                            • связи ссылаются на существующие ноды
                            • ровно один триггер
                            • нет висячих нод
                                  │
                                  ▼
                          tools/deploy.js
                            • PUT если workflow с таким именем уже есть
                            • POST если новый
                            • settings фильтруются по белому списку
```

### Почему `settings` фильтруются

Public API n8n принимает в теле только `name`, `nodes`, `connections`, `settings`.
Всё остальное (`id`, `active`, `versionId`, `createdAt`, `tags`, `meta`) — read-only,
и при попытке их передать API отвечает `400`. В `settings` тоже разрешён не любой ключ:
лишний ключ даёт `400 settings must NOT have additional properties`.
Поэтому в `tools/deploy.js` есть явный белый список — это не перестраховка,
а обязательное условие работы.

### Почему деплой не активирует поток

`active` через public API не меняется. Это сделано намеренно: активация — отдельное
осознанное действие. Пайплайн доставляет новую версию, но не включает её сам.

## Структура

```
.
├── src/
│   ├── code/                 логика Code-нод, обычные модули
│   │   ├── normalize-lead.js
│   │   └── score-lead.js
│   └── workflows/            описания потоков
│       └── lead-router.js
├── tools/
│   ├── build.js              сборка JSON из кода
│   ├── validate.js           проверки до деплоя
│   └── deploy.js             доставка в n8n через API
├── .github/workflows/ci.yml  пайплайн GitHub Actions
├── .gitlab-ci.yml            тот же пайплайн для GitLab
├── docker-compose.yml        локальный стенд n8n + PostgreSQL
└── dist/                     артефакты сборки, в git не хранятся
```

## Пример потока

`lead-router` — маршрутизация входящей заявки: приём вебхука → нормализация полей →
скоринг по поведенческим метрикам → ветвление по приоритету → ответ.

Это упрощённый, обезличенный пример: он показывает механику сборки, а не реальную
бизнес-логику. Скоринг считает средневзвешенное по метрикам визита с логарифмическим
сглаживанием и нормализацией к шкале 0–10 — тот же приём, что применяется
для приоритизации заявок в реальных системах.

## Что бы я добавил дальше

Честный список того, чего в этом репозитории пока нет:

- **Покрытие тестами шире.** Сейчас 15 тестов на нормализацию, скоринг и сборку.
  Не хватает тестов на сам валидатор — проверок, что он действительно падает
  на битых потоках, а не только пропускает целые.
- **Отдельные окружения dev/prod** с разными наборами секретов и правилом,
  что в prod едет только то, что прошло dev.
- **Смоук-прогон после деплоя:** дёрнуть тестовый вебхук и убедиться, что поток отвечает,
  а не просто «доставился».
- **Диффер против прода:** показать, чем собранная версия отличается от текущей в n8n,
  до того как нажимать деплой.
